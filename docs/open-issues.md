# Shoka 未決事項

## 1. 実装前に解決する検証事項

### 1.1 データ源の構成

状態: 採用済み

楽天Books Book Search APIだけを利用する。著者検索、基本書誌、書影、内容紹介を同じ商品レコードから取得し、ISBNを使った複数データ源間の結合は行わない。購入導線は目的ではないため、価格、在庫、レビュー、アフィリエイト情報は表示しない。

2026-09-21に東野圭吾で実データを確認した。総件数315件が返り、1ページ目は30件すべてに書影、28件に内容紹介があった。1ページ目末尾の1992年4月から2ページ目先頭の1992年6月へ刊行順が継続し、両ページ間にISBN重複はなかった。

確認すること:

- 東野圭吾を含む代表著者で総件数と最大100ページまでの取得が安定するか
- 楽天Booksの検索結果から対象外の商品をどこまで識別できるか
- 書影、判型、発売日、出版社、内容紹介の欠損率
- 同じISBNまたは商品が重複するケース
- 著者名の区切り方と共著者表現
- 楽天Books APIのクレジット、キャッシュ、更新・削除反映の条件

判断基準:

- 外部レスポンスを内部モデルへ無理なく正規化できる
- 代表著者で書影が一覧体験を成立させる割合で取得できる
- 欠損してもプレースホルダーと項目省略で破綻しない

### 1.2 単著・共著フィルター

状態: 未決

各データ源の著者フィールドが役割を厳密に表現しない場合、監修・原作・翻訳などを完全には除外できない可能性がある。

検証後に次のどちらかを選ぶ。

1. 安全に判定できる表現だけを掲載する
2. 著者名を含む項目を広めに掲載し、役割誤判定を既知の制約として明示する

推奨は1。ただし正しい単著・共著まで多く欠落する場合は2を再検討する。

### 1.3 著者候補の生成

状態: 未決

楽天Booksの書籍検索結果から著者候補を導出する場合、次を検証する。

- 部分一致検索で候補を安定抽出できるか
- 共著者文字列を誤って一人の著者として扱わないか
- 同じ人物の表記揺れをどこまでまとめられるか
- 完全一致一件の判定が安全か

著者候補は名前だけ表示する決定を維持し、補助情報は実利用で必要になった場合だけ追加する。

### 1.4 Vercel上のAPI実行制約

状態: 未検証

Vercel上のRoute Handlerで、次の処理が実用的な応答時間とレスポンスサイズに収まるか計測する。

- 楽天Books APIの複数ページ取得とJSON正規化
- 対象書籍フィルター
- 日付とISBNの正規化
- 全件の出版年ソート
- キャッシュへの保存または取得

制約を超える場合の検討順:

1. 変換処理の単純化
2. ページ単位キャッシュと遅延正規化
3. Vercelのキャッシュ機能やデータ保存方式の見直し
4. 有料プランへの移行

MVPの運用費0円制約があるため、4は最後の選択肢とする。

### 1.5 masonryの視覚順と操作順

状態: 未検証

CSS GridとResizeObserverによる配置で、次を実機確認する。

- DOM順と視覚上の順序が利用者を混乱させない
- 画像読み込み後の移動が小さい
- 無限追加時に既存カードが大きく移動しない
- iOS Safariを含む対象ブラウザで安定する
- フォールバックの通常グリッドでも利用可能

アクセシビリティと安定性が損なわれる場合は、完全なmasonryより通常グリッドを優先する。

## 2. 公開前に確認する事項

### 2.1 データ源の利用条件

- 楽天ウェブサービスのアプリIDとアクセスキーを本番環境へ設定する
- 許可Webサイトと一致する`RAKUTEN_APP_URL`を本番環境へ設定する
- 楽天Books APIに必要なクレジット、画像表示、キャッシュ条件を確認する
- APIのレート制限と禁止事項を確認する

利用条件が本仕様と衝突する場合は利用条件を優先し、データ源または表示内容を変更する。

### 2.2 Vercel標準ログ

- 無料枠で標準生成されるログ
- IPアドレスなどの保持有無
- 保持期間と無効化可否

アプリ独自の計測は実装しない。

### 2.3 Shokaの名称

- 現在は仮称
- 国内主要サービスとの明確な重複は簡易検索で見つからなかった
- 商標の正式調査は未実施
- 独自ドメインはMVP対象外
